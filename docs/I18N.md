# Internationalization & localization status: gettext (EN/ES/FR/AR, incl. RTL)

ledger renders its end-user-facing text in **English, Spanish, French, and Arabic**
through GNU **gettext** message catalogs, per
[`portfolio-standards/INTERNATIONALIZATION-STANDARD.md`](https://github.com/ChelseaKR/portfolio-standards/blob/v1.0.1/INTERNATIONALIZATION-STANDARD.md)
§3/§4. Arabic is right-to-left, so the browse pages carry a base text direction
(`<html dir="rtl">`, see [RTL & text direction](#rtl--text-direction-g10)). This
replaces the previous bespoke `_CATALOG`/`_CW_GLOSSES` Python dicts in `ledger.i18n`
(which had no extraction tooling, no plural handling, and no key-parity check).

Declared: 2026-06-30 · Updated: 2026-07-02 (RM7: +fr/+ar, RTL, remaining gates)
· Reviewer: ledger maintainers

---

## What is (and is not) translated

**Translated — the accessible browse server + contribution form.** The rendered
HTML surface ([`ledger.render`](../src/ledger/render.py),
[`ledger.server`](../src/ledger/server.py),
[`ledger.contribute`](../src/ledger/contribute.py)) is where ledger emits
end-user-facing, natural-language text: navigation and search chrome, the
collection overview, record pages and content-warning glosses, the steward console
and audit log, the consent/takedown status lookup, and the whole contribution write
path (form, "what a stranger sees" preview, confirmation, edit, and withdrawal, plus
the contributor-facing validation messages). Every such fixed string resolves
through the gettext seam and is rendered in the negotiated language.

**Not translated — operator/developer text (English-only by design).** The standard
scopes i18n to end-user text, not operator logs, so these are deliberately left in
English and carry **no** gettext calls:

- the CLI status/notice output and `argparse` help ([`ledger.cli`](../src/ledger/cli.py));
- the public-submission **moderation** output;
- PREMIS/Dublin Core preservation-metadata field text and structured event records;
- any diagnostic/status string not shown to an archive visitor or contributor.

Language **autonyms** (`language_name`: `English`, `Español`, `Français`,
`العربية`) are intentionally *not* gettext-translated — an autonym is invariant
across the UI language, so a language picker always reads naturally to a native
speaker.

## RTL & text direction (G10)

`ledger.i18n.text_direction(lang)` returns `"rtl"` for a right-to-left script
(primary subtag in `{ar, he, fa, ur}`, matched case-insensitively so `ar-EG`
resolves) and `"ltr"` for everything else, including an unknown or malformed tag
(the safe default — a page never renders with an empty or wrong direction). The
shared page shell (`ledger.render._page`) threads this into the document root, so
every rendered page declares both the language and its direction:

```html
<html lang="ar" dir="rtl">   <!-- Arabic: right-to-left -->
<html lang="fr" dir="ltr">   <!-- French/English/Spanish: left-to-right -->
```

Because `dir` is set on `<html>`, the browser mirrors the whole layout for an RTL
reader with no per-element CSS. Adding another RTL language is just adding its
catalog and (if its primary subtag is new) one entry to `_RTL_LANGS`.

That claim is now checked by a browser rather than only asserted. The
`chromium-rtl` project in `tools/a11y_browser/playwright.config.ts` negotiates
Arabic and runs the axe and 320px reflow gates over the whole canonical surface with
the layout actually mirrored. It was worth checking: the first run found
`.skip-link` parked at `left: -9999px`, the old off-screen idiom, which is harmless
under `ltr` and 9,999 pixels of real horizontal scroll under `rtl` — a WCAG 2.2 SC
1.4.10 failure that "no per-element CSS" had been hiding, in every RTL page, since
`ar` shipped. It is now clipped rather than displaced, and the reflow gate reads the
inline **end** edge, which is the left one under `rtl`.

## The seam (how it works)

- [`src/ledger/i18n.py`](../src/ledger/i18n.py) is the single migration seam.
  `get_translation(lang)` loads `messages.mo` for the language with
  `fallback=True` (an unknown tag or a missing `.mo` returns the English source
  text, never an error). `negotiate(accept_language, available)` implements the §6
  `Accept-Language` fallback chain (`<requested> → <primary subtag> → site
  default (en)`), honoring `q` weights.
- **The public API is unchanged**, so no render/server/contribute call site moved:
  `t(lang, key, **kw)`, `gloss_cw(lang, tag)`, `language_name(code)`, and
  `negotiate(...)` keep their signatures. Internally they now resolve through
  gettext instead of a hand-maintained dict. `t` looks a stable UI key up in a
  `{key: _("English source")}` map built from the loaded catalog, so the
  **source string is the English text itself** — extraction needs no key map.
- Catalogs live **inside the package** at
  `src/ledger/locales/{messages.pot, <lang>/LC_MESSAGES/messages.{po,mo}}`, so a
  checkout or an installed wheel resolves them with no separate install step.
- [`babel.cfg`](../babel.cfg) tells `pybabel extract` to scan the package sources.

### Plurals

Messages with genuine singular/plural forms use `ngettext` (full CLDR plural
categories: `nplurals=2` for en/es/fr, `nplurals=6` for Arabic — the `pybabel init`
header carries the right rule and slot count per locale): the "edited N times"
steward badge
(`badge_edited`) and the "N details are restricted" outsider notice
(`rec_withheld_outsider`). The two record-count display strings (`overview_total`,
`results_showing`) keep their established `record(s)` single-message form rather
than being split into `ngettext`: they are asserted verbatim across the
pagination/overview/server/browse tests, and converting them buys no
plural-correctness the `(s)` form does not already convey, while widening the blast
radius into the disclosure/server suites. This is a deliberate, recorded scope
decision, not an oversight.

## Translation status — es/fr/ar all complete (no backlog)

Complete here means **filled in**, and that is a different claim from **reviewed**.
See [Translation review](#translation-review-drafted-not-reviewed) below, which is
the one this page used to get wrong.

**Spanish** is a **format migration of an existing translation**: `_CATALOG["es"]`
and `_CW_GLOSSES["es"]` were already complete Spanish, carried over **verbatim**
into `es/LC_MESSAGES/messages.po`. (This paragraph read "human-authored Spanish"
until 2026-09-07. Nothing in this repository establishes that — the dicts were
written in-project, like the rest of it — so the word came out.)

**French** (`fr/LC_MESSAGES/messages.po`) and **Arabic**
(`ar/LC_MESSAGES/messages.po`) were authored for RM7: every msgid (including both
plural cases, and Arabic's six CLDR plural forms) and every content-warning gloss is
translated, with `{…}` placeholders preserved so the placeholder-parity gate holds.

Because every shipped locale is complete, the **G5 completeness gate is enforced as
a hard merge-blocker** — every msgid has a non-empty `msgstr` in **every** locale
(en/es/fr/ar), including every plural form — *not* downgraded to a structural-only
check. There is no
[REVIEW-GATE R3](https://github.com/ChelseaKR/portfolio-standards/blob/v1.0.1/INTERNATIONALIZATION-STANDARD.md#5-review-gates-human-judgment--committed-artifact)
translation backlog for the current string set. Any *new* user-facing string is
added in English first and must have its `msgstr` filled in **all four** locales
before merge (the gates below block otherwise). Community translators are the
intended path for further review/refinement of the fr/ar strings.

## Translation review: drafted, not reviewed

**No qualified speaker of Spanish, French or Arabic has reviewed these catalogs.**
`ledger.i18n.REVIEWED_LOCALES` is empty, and that empty set is the honest value
rather than a placeholder — adding a locale to it is a claim about a person, so it
is a human's edit to make, recording who reviewed it and when, here.

### What the gate can now establish, and what it still cannot

The numbered gates check three things — key parity (G6), completeness (G5: every
`msgstr` non-empty), and placeholder parity (G5). **A Spanish `msgstr` that is
verbatim English satisfies all three.** It is non-empty, its key matches its
msgid, and its `{…}` placeholder set is trivially identical. `make i18n` printed
`catalog parity OK` over a catalog nobody had translated, and that is exactly what
it would keep printing.

`tools/check_catalog_parity.py` now carries an **identity check** as well (ported
from `fare-policy-assistant`, which measured the same hole first): `en` is the
source language, so its `msgstr` must **equal** its `msgid`, and every other
catalog's must **differ** from it.

A blanket must-differ rule would be the wrong repair, and wrong in the direction
that gets a gate switched off. Measured on this repository, 2 of 273 Spanish
msgstrs and 6 of 273 French ones are byte-identical to their msgid, and every one
is correct: `No` is `No` in Spanish; `Agent`, `Date`, `Description`, `Pagination`,
`Type` and `Types` are the French words too. So the rule has three ways out, and
only the third is a judgement:

1. **Nothing to translate.** With `{placeholders}` removed the msgid has no
   alphabetic character — a bare number, `$2.50`, a lone `{count}`.
2. **A code token, not prose.** A single all-caps token (`OK`, `CSV`, `PDF`,
   `WCAG`) or a bare URL. Upper case is required deliberately, so `Help`, `Date`
   and `Type` are short words rather than acronyms and stay in scope — which is
   precisely what a blanket rule gets wrong in both directions.
3. **A written reason** in
   [`src/ledger/locales/identical_by_design.json`](../src/ledger/locales/identical_by_design.json).
   ledger has **eight** entries, all of them cognates the committed catalogs
   already chose; none is a new translation decision, and none has been read by a
   qualified speaker any more than the catalogs have. The list is self-limiting:
   an entry with no reason is refused, and an entry whose msgid the template no
   longer declares — or whose msgstr has since been translated — fails the gate
   until it is deleted.

**It still cannot tell good Spanish from bad Spanish.** It fails a catalog that was
never translated; it says nothing about how a translation reads to a speaker of the
language. That is what the review declaration below is for.

### What is disclosed instead, in three places

| Where | What it says | Enforced by |
|---|---|---|
| `tools/check_catalog_parity.py` | every non-source `msgstr` differs from its English msgid, or is mechanically untranslatable, or carries a written reason | the gate itself, plus `tests/test_catalog_review_gate.py` |
| Each non-source `.po` | a `TRANSLATION REVIEW: drafted` comment above the header entry, and an `X-Translation-Review: drafted` header field | `tools/check_catalog_parity.py` requires the field to equal `ledger.i18n.translation_review(<locale>)`, so the code and the catalog cannot drift apart |
| Every rendered page in that language | a `role="note"` banner, **in that language**, saying the translation was drafted by the project and not reviewed by a qualified speaker | `tests/test_i18n_rtl.py`, derived from `SUPPORTED` so a new locale is covered without editing the test |
| This page and `README.md` | the same fact in prose | — |

`translation_review` has **three** states, not two: `source` (English — the
msgids themselves, so there is nothing to review), `reviewed`, and `drafted`. An
unknown or unshipped tag is `source`, because `get_translation` falls back to the
English msgids for it and what that reader is served is the source text. Calling
it "unreviewed" would be the mirror of the defect the disclosure exists for:
reporting a translation nobody made as one nobody checked.

### What would change this

A qualified speaker reads a locale's catalog and says so. Then: add the tag to
`REVIEWED_LOCALES`, change that catalog's `X-Translation-Review` to `reviewed`,
record the reviewer and the date in this section, and `make i18n-compile`. The
banner stops rendering for that language on its own — nothing else to remember,
because the page reads the same declaration the gate does.

## Live merge-blocking gates (`make i18n`, wired into `make verify` and CI)

Local `make i18n` and the CI `i18n` job run the identical target (no drift):

| Gate | What it checks | Mechanism |
|---|---|---|
| **G1** | UTF-8 end to end | [`tools/check_i18n_utf8.py`](../tools/check_i18n_utf8.py): every `.po`/`.pot` decodes as strict UTF-8 and declares `charset=utf-8`; a page rendered in each locale round-trips through UTF-8 and declares `<meta charset="utf-8">`. |
| **G2-lite** | The extraction template is committed & current | `pybabel extract` → normalize → `git diff --exit-code` on `messages.pot`. A new/changed user-facing string without a re-extract fails. |
| **G3** | BCP 47 / RFC 5646 tag validity | [`tools/check_bcp47.py`](../tools/check_bcp47.py): `babel.Locale.parse` on every authored locale tag |
| **G5** | Completeness + placeholder parity | [`tools/check_catalog_parity.py`](../tools/check_catalog_parity.py): every `msgstr` (each plural form, incl. Arabic's six) non-empty; `{...}` field set identical source↔target |
| **G6** | Key-parity across every locale | same script: msgid sets of `en`/`es`/`fr`/`ar` are each identical to the template (hence to one another) |
| **G7** | Every PO compiles cleanly | `msgfmt --check --check-format --check-domain` on each locale's `messages.po` |
| **G9** | Pseudolocale (test-only) | `i18n.pseudolocalize` accent-wraps a string keeping `{…}` intact; `tests/test_i18n_rtl.py` renders the **whole shared shell** through it, strips every `⟦…⟧` span, and asserts the only Latin-script text left is the named invariants (the language autonyms and the product name `ledger`). The **body** of each safety-surface route (`/about`, `/governance`, `/how-it-works`) gets the same treatment against the served page, where the named exception is the steward-authored config text instead. Never a shipped locale. See [What G9 used to check](#what-g9-used-to-check-and-why-it-found-nothing). |
| **G10** | RTL direction | `i18n.text_direction` → `<html lang dir>`; asserted for `ar` (rtl) vs en/es/fr (ltr), and **rendered**: the `chromium-rtl` Playwright project drives the canonical pages in Arabic through axe and the 320px reflow check, and `direction.ts` refuses a run whose document did not come back `rtl`. |
| **G11** | `Content-Language` + `Vary` | `ledger.server._send` emits `Content-Language: <negotiated>` and `Vary: Accept-Language` on **every** response; asserted across HTML/text/JSON routes. |
| **G12** | CLDR / locale-data freshness pin | [`tools/check_i18n_deps.py`](../tools/check_i18n_deps.py): Babel within the reviewed `>=2.16,<3` range and its bundled CLDR data loads (plural categories + display names resolve). |

`msgfmt` is a system **gettext** binary (like `gitleaks`, not a pip dependency); CI
installs it with `apt-get install -y gettext`. `pybabel`/`babel.Locale` come from
the `babel>=2.16,<3` dev dependency (pure Python — no PyICU/native ICU build, so
ledger keeps its "run on one inexpensive box, no heavy dependency tree" property).
The upper bound is the **G12** CLDR ceiling: a new Babel major bundles a new CLDR
release and must be adopted deliberately, not picked up silently.

### What G9 used to check, and why it found nothing

This table described G9 as asserting "no un-wrapped (hardcoded) English leaks", and
that was the intent. The test asserted something narrower:

```python
for plain in ("Browse", "Search", "Overview", "Skip to main content"):
    assert plain not in page
```

All four already go through the seam. **The gate could only find hardcoded English in
the set of strings that are not hardcoded.** It was green over five real leaks in the
page shell — every one of them on every page — from the day `ar` shipped:

| where | string |
|---|---|
| `render._nav_html` | `Contribute` — one of nine navigation links, and the only one not localized |
| `render._page` | `Reference implementation — sample data is synthetic.` |
| `render._page` | the brand tagline `community archive` |
| `render._page` | `Governance` |
| `render._page` | `How it works` |

An Arabic reader got an RTL page whose navigation ended in the English word
**Contribute** — the link inviting them to give this archive their material — and
whose footer read `حول · Governance · How it works`.

The check now works the other way round. Every string resolved through `i18n.t` comes
back bracketed by `PSEUDO_PREFIX`/`PSEUDO_SUFFIX`, so the test removes those spans and
looks at what is left. Tags are stripped whole, which drops `href`, `lang` and
`hreflang` values — Latin by necessity, and not prose. What remains must be in a named
allowlist with a stated reason, currently the three autonyms and `ledger`.

It is deliberately **not** written as "assert every word is accented":
`_PSEUDO_MAP` leaves `m`, `q`, `v`, `w` and `x` as themselves, so accent-detection
would quietly pass a hardcoded word built only from those letters.

**Scope.** The shell check covers banner, brand, nav and footer, which every page
renders, and it is deliberately rendered with an empty `<main>` — so it is blind to
every page *body* by construction. Two bodies now have their own check:

* `/status` — every sentence went through the seam in
  [#218](https://github.com/ChelseaKR/ledger/pull/218), tested against the served page.
* `/about`, `/governance`, `/how-it-works` — the plain-language safety surface. Same
  test, applied to each route's `<main>`: render it under the pseudolocale, strip the
  `⟦…⟧` spans, and require what is left to be nothing but the **steward-authored
  config text** ledger cannot translate (`Config.about` and `Config.steward_vetting`,
  passed through as paragraphs). The fixture sets those two fields to unique nonsense
  tokens, so the assertion names exactly what may survive instead of subtracting a
  paragraph of English. `operators`, `contact` and `consent_response_time` are
  interpolated *into* seam strings, so they come back inside the wrapper.

Every route's body still needs its own entry here; a green shell says nothing about
one. The cheap way to find the next gap is to compare the strings a route renders
against `grep -c '^msgid' messages.pot`.

### The POT normalizer

`pybabel extract` emits volatile tokens (creation timestamp, Babel version, the
current year in the boilerplate comment) and would tag any literal-`%` string as a
false `python-format` (printf) message.
[`tools/i18n_normalize_pot.py`](../tools/i18n_normalize_pot.py) freezes those tokens
and drops the spurious flag so the G2-lite diff is meaningful, not flaky, and so
`msgfmt --check-format` never wrongly rejects a literal percent sign. The gate runs
the normalizer on both authoring and CI, keeping the committed POT byte-stable.

## Compiled `.mo` files are committed

The compiled `messages.mo` catalogs **are committed** (not gitignored). Rationale:
ledger's CI runs single `make`/`pytest` steps per job with no packaging/build step,
and the test suite renders the browse pages and asserts translated output, so the
catalogs must be present at runtime. Committing `.mo` keeps every job green with
local == CI and no extra per-job compile, and ships the translations in the wheel.
Regenerate `.mo` for **all four** locales after editing a `.po` with
**`make i18n-compile`**.

**G13 — the shipped `.mo` says what the reviewed `.po` says.** This page
used to say `.po` ↔ `.mo` drift was "guarded end-to-end by the render/server tests".
It was not. Those tests assert a handful of specific strings (`"Browse"` →
`"Explorar"`), so they guard those strings and nothing else: changing any other
`msgstr` and skipping `make i18n-compile` left the whole suite green, G5/G6/G7
included, while the program served the old translation. Measured on this repository:
one edited Spanish `msgstr`, no recompile, 1295 tests passed. The compiled catalog was
a committed artifact standing in for a computation nothing re-ran.

[`tools/check_mo_current.py`](../tools/check_mo_current.py) now reads each committed
`.mo` with `gettext` (the same reader `ledger.i18n.get_translation` uses at runtime, so
what is compared is what the program will actually serve), reads the `.po` with Babel,
and requires the two message maps to be equal in both directions. It writes nothing: a
gate that recompiles the artifact it is judging heals drift on the contributor's disk
while the committed bytes stay stale.

**It compares meaning, not bytes, and that was a correction.** The first version compiled
each `.po` into a temp dir with `msgfmt` and compared byte for byte. That passed locally
and failed in CI on an unmodified tree:

| msgfmt | result against the committed `.mo` |
| --- | --- |
| GNU gettext-tools 1.0 (macOS, Homebrew) | byte-identical |
| GNU gettext-tools 0.23.1 (Debian trixie) | byte-identical |
| GNU gettext-tools 0.21 (Debian bullseye) | same length, different bytes, **identical message map** |

The MO format carries a hash table whose layout msgfmt has changed between releases, so
byte equality is a property of *which msgfmt ran*, not of the catalog. Gating it would
have pinned every contributor and every runner to one gettext build, or led to the gate
being weakened later when it went red for no reason. What G13 excludes is named and
short: the MO byte layout, and header fields other than `Plural-Forms`. `Plural-Forms`
is compared, because a stale one selects the wrong plural at runtime.

## Workflow: adding or changing a user-facing string

1. Add the string to the `_messages` (or `_cw_glosses`) map in
   [`src/ledger/i18n.py`](../src/ledger/i18n.py) as `"key": _("English source")`
   (or, for a count, add an `ngettext(...)` case to `_plural_message` and register
   the key in `_PLURAL_KEYS`). Use `.format()` placeholders (`_("… {n} …")`).
2. `make i18n-extract` — rewrites `messages.pot`; then `make i18n`, whose G2-lite step
   re-extracts into a temporary directory and diffs, showing the new msgid. `make i18n`
   itself writes nothing: it is a merge gate, and a merge gate that regenerates the
   artifact it is judging cannot tell you the committed one was stale.
3. Merge the new msgid into every catalog (`pybabel update -i
   src/ledger/locales/messages.pot -d src/ledger/locales --no-fuzzy-matching`),
   then fill the `msgstr` in **all four** locales — English (= msgid), Spanish,
   French, and Arabic (all six plural forms for a count in `ar`). The G5 gate blocks
   an empty `msgstr` in any locale.
4. `make i18n-compile` to rebuild the `.mo`, then `make i18n` (and `make verify`).
5. Commit the changed `.py`, `messages.pot`, all four `messages.po`, and all four
   `messages.mo`.

### Workflow: adding a new UI language

1. `pybabel init -i src/ledger/locales/messages.pot -d src/ledger/locales -l <tag>`
   (this writes the correct `Plural-Forms` and slot count for the locale), then
   `pybabel update -i src/ledger/locales/messages.pot -d src/ledger/locales
   --no-fuzzy-matching` to keep it in step with the template.
2. Translate every `msgstr` (all plural forms), preserving `{…}` placeholders.
3. Add the tag to `SUPPORTED` and an autonym to `_LANGUAGE_NAMES` in `ledger.i18n`.
   If it is a **right-to-left** language whose primary subtag is not already in
   `_RTL_LANGS`, add it there so `text_direction` returns `"rtl"` and the page shell
   emits `<html dir="rtl">`.
4. `make i18n-compile`, then `make i18n && make verify`. The parity/completeness,
   UTF-8, BCP-47, and CLDR gates all pick the new locale up automatically (they
   iterate `SUPPORTED`).

## Scope now covered (RM7)

All i18n gates in the standard are now live in `make i18n`/`make verify`:
G1 (UTF-8), G2-lite (POT current), G3 (BCP-47), G5 (completeness/placeholder),
G6 (key-parity across en/es/fr/ar), G7 (PO compiles), G9 (test-only pseudolocale),
G10 (RTL `dir`), G11 (`Content-Language` + `Vary` on every response), and G12
(CLDR/Babel freshness pin). See the gates table above for each mechanism.

**G4** (`html-has-lang`) is covered by the accessibility gate rather than the i18n
gate: the browse pages set `lang` **and** `dir` on `<html>`, and
`make accessibility` (axe-style checks over the rendered surface) enforces it. CLDR
data remains whatever the pinned `babel` bundles; the G12 upper bound (`babel<3`)
makes bumping it a deliberate, reviewed step per the standard's cadence.
